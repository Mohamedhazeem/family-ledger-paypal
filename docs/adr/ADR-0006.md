# ADR-0006: PayPal Payouts integration: idempotency via sender_batch_id, PayoutAttempt persistence, uncertain-outcome handling, no duplicate submits
- Status: Accepted
- Date: 2026-11-06
- Deciders: Tech Lead, Founding Engineering
- Spec refs: Part C §11, Part B §Steps 8–9, Part A §4 #1,3,9
- Supersedes: none

## Context
Payouts API: duplicate `sender_batch_id` reuse within 30 days is rejected (no duplicate processing); 5xx/timeout is uncertain; double-click must not double-pay.
## Decision
Server-only PayPal service (`services/paypal/`). Persist unique `sender_batch_id`/`sender_item_id` in `PayoutAttempt` **before** call; DB conditional lock for concurrency; reuse same ID on 5xx/timeout; stay `SUBMITTING`/`STATUS_UNKNOWN` until real result; preserve unknown statuses; fetch batch via `GET /v1/payments/payouts/{id}`.
## Consequences
### Positive
- Duplicate-safe, auditable, honest status reporting.
### Negative / trade-offs
- Operator reconciliation needed for UNKNOWN state.
### Risks & mitigations
- New ID on retry — reuse; atomic update guards races.
## Alternatives considered
Retry with new ID — rejected: risks duplicate payment, violates spec.
## Implementation guardrails
- MUST persist before call; MUST NOT generate new `sender_batch_id` on 5xx/timeout; MUST show batch vs item status separately; MUST use only official API fields.
## Verification
- Integration tests: persistent-before-call, 5xx/timeout handling, duplicate-click Playwright, batch/item mapping.
