# ADR-0019: Coordinator plan revision, amount adjustment and clarifications
- Status: Accepted
- Date: 2026-11-11
- Deciders: Tech Lead, Founding Engineering
- Spec refs: Part C §6 Steps 5–7, §9 (PlanVersion immutability), §10 (PlanStatus), §13 (recipient cannot change amount)
- Supersedes: none

## Context
After a beneficiary suggests changes, the coordinator needs to respond. Spec §6 Step 7 lists acknowledge / ask one clarification question / continue without acknowledgment / proceed with payout, and says the coordinator must not overwrite the beneficiary's response. The MVP shipped only "acknowledge" — "ask one clarification question" was unimplemented, and there was no way to adjust the proposal (categories or total) after the invitation.

## Decision
1. Coordinator revision (`ProposeCoordinatorRevision`): the coordinator may edit categories and the full amount, which appends a NEW immutable PlanVersion (`createdByType = COORDINATOR`). `planStatus` is set to `REVISION_PROPOSED` for any pending revision; the version's `createdByType` records the author. No PlanStatus enum change.
2. Guard: `paymentStatus === NOT_SENT`. Once a payout exists the amount and plan are locked. Allocations are validated against the (possibly new) total before any write.
3. Clarification questions (`PlanClarification`): the coordinator asks one question; the latest unanswered question is shown in the beneficiary portal; a new beneficiary suggestion marks it answered. Emits the existing `PLAN_CLARIFICATION_REQUESTED` ledger event.
4. "Acknowledge plan" is hidden while the latest version was proposed by the coordinator (a coordinator cannot acknowledge their own proposal).

## Consequences
### Positive
- The coordinator can act on a beneficiary suggestion without overwriting it; the loop is suggestion → adjustment/clarification → response.
- The amount stays fixed once money moves.
### Negative / trade-offs
- Deviates from the Step 7 action list (adds coordinator editing). Recorded here as the governing decision.
- `REVISION_PROPOSED` is reused for both authors; the version badge carries the distinction.
### Risks & mitigations
- Changing the amount after a payout — blocked by the NOT_SENT guard.
- Over-total plan after an amount change — deterministic validation before any write.
- Clarification question leakage — only the question is stored/shown to the beneficiary; the ledger payload carries the id only.

## Alternatives considered
- New `PlanStatus` value — rejected: enum churn for no behavioural gain; `createdByType` already distinguishes authors.
- Coordinator edits the version in place — rejected: PlanVersion is immutable (spec §9).

## Implementation guardrails
- Only append versions; never update a PlanVersion.
- Only adjust while NOT_SENT; never log the question text in the ledger.
- Do not gate payment on plan status (spec §4.4).

## Verification
- Unit tests: guards, over-total, amount update, clarification storage.
- Integration tests over real Prisma: version appended, amount updated, clarification marked answered.
- E2E: adjust proposal → Version 2 (Coordinator) → ask clarification → portal shows the question.
