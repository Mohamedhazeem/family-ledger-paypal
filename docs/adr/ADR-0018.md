# ADR-0018: Soft delete for never-sent drafts
- Status: Accepted
- Date: 2026-11-11
- Deciders: Tech Lead, Founding Engineering
- Spec refs: Part C §9 (`LedgerEvent` append-only, ADR-0009), Part C §13 (audit/privacy), Part G §21 (MVP scope)
- Supersedes: none

## Context
Coordinators save draft disbursements (`planStatus = DRAFT`, `paymentStatus = NOT_SENT`) that are sometimes wrong or duplicated. The spec defines no delete capability, and `LedgerEvent` is append-only (ADR-0009), so a hard `DELETE` would either destroy audit history or fight the schema's `onDelete: Restrict` relations (PlanVersion, LedgerEvent, RecipientInvitation, PayoutAttempt).

## Decision
Add `Disbursement.deletedAt DateTime?`. A `DeleteDisbursement` use case soft-deletes a draft only when `paymentStatus === NOT_SENT`: it revokes active invitations, stamps `deletedAt`, and appends a `DISBURSEMENT_DELETED` ledger event. Read surfaces (dashboard, register, detail page/API, analytics) filter `deletedAt: null`; the beneficiary portal and pay submission also refuse deleted rows.

## Consequences
### Positive
- Drafts can be discarded without losing the append-only audit trail.
- No cascade/`Restrict` problems; the operation is reversible.
### Negative / trade-offs
- Deleted rows remain in the database; every read query must filter.
- `publicReference` stays reserved (unique constraint untouched).
### Risks & mitigations
- A deleted draft being paid — `claimForSubmission` requires `deletedAt: null`, and `SubmitPayout` rejects deleted rows outright.
- A previously shared link still resolving — delete revokes active invitations, and `GetInvitationView` independently rejects a deleted disbursement.

## Alternatives considered
- Hard `DELETE` with cascade — rejected: deletes `LedgerEvent` history (violates ADR-0009) and fights `onDelete: Restrict`.
- New `PlanStatus` value (`DELETED`/`ARCHIVED`) — rejected: `PlanStatus` is a fixed enum that would need its own ADR, and it conflates the plan lifecycle with record lifecycle.

## Implementation guardrails
- Delete only through the use case; never hard-delete from application code.
- Keep the `NOT_SENT` guard: a disbursement that reached `READY`/`SUBMITTING`/`FAILED` or any PayPal outcome is never deletable.

## Verification
- Unit tests: guards (`NOT_SENT` only, owner only, already-deleted) + invitation revocation.
- Integration test over real Prisma adapters: soft delete, portal 404, read surfaces exclude the row.
- M-check against `next start`: send plan → delete → portal 404 → register/dashboard hide the reference → second delete returns 404.
