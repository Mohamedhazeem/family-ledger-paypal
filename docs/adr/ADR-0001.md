# ADR-0001: Single-deployable full-stack: Next.js App Router + TypeScript
- Status: Accepted
- Date: 2026-11-06
- Deciders: Tech Lead, Founding Engineering
- Spec refs: Part C §7 (Recommended stack), Part C §8 (Source structure), Part F Day 1
- Supersedes: none

## Context
Six-day hackathon window; coordination across frontend, API, AI, PayPal, analytics, DB would slow delivery with microservices. Spec recommends one TypeScript codebase.
## Decision
Use Next.js App Router + TypeScript as single deployable. Frontend and server Route Handlers in one app on Render.
## Consequences
### Positive
- One build/ship path, shared types, fastest vertical slices; fits Render Web Service target.
- Easy TDD with Vitest + Playwright in one repo.
### Negative / trade-offs
- Larger single codebase; requires strict module boundaries to avoid god-files.
- Tied release cadence for UI and API.
### Risks & mitigations
- Scope creep into one file — enforce 300 LOC policy (ADR-0013) and thin Route Handlers.
## Alternatives considered
Separate frontend + API services — rejected: over-engineering, more infra, slower hackathon velocity.
## Implementation guardrails (what future code MUST/MUST NOT do)
- MUST keep Route Handlers thin (see ADR-0011).
- MUST deploy as one Render Web Service.
- MUST NOT add separate Python/microservices.
## Verification (tests or checks that prove this decision is respected)
- `next build` succeeds from single `package.json`; Playwright E2E runs against same app.
