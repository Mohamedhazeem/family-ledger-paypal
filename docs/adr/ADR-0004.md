# ADR-0004: Two independent state machines: planStatus vs paymentStatus
- Status: Accepted
- Date: 2026-11-06
- Deciders: Tech Lead, Founding Engineering
- Spec refs: Part A §4 #10, Part C §10, Part B §Steps 1–10
- Supersedes: none

## Context
Beneficiary acknowledgement must not gate payment; consent voluntary.
## Decision
Separate `PlanStatus` (`DRAFT`, `INVITED`, `BENEFICIARY_ACCEPTED`, `REVISION_PROPOSED`, `COORDINATOR_ACKNOWLEDGED`, `BENEFICIARY_DECLINED_TO_SHARE`, `NO_RESPONSE`, `CLOSED`) and `PaymentStatus` (`NOT_SENT`, `READY`, `SUBMITTING`, `STATUS_UNKNOWN`, `PENDING`, `PROCESSING`, `SUCCESS`, `DENIED`, `FAILED`, `UNCLAIMED`, `RETURNED`, `ON_HOLD`, `BLOCKED`, `REFUNDED`, `REVERSED`) enums. Keep PayPal batch status separately from item status.
## Consequences
### Positive
- Audit clarity; beneficiary can decline and still be paid; honest PayPal reporting.
### Negative / trade-offs
- Two progress tracks to explain in UI.
### Risks & mitigations
- Collapsing statuses in UI — preserve unknown, show raw + friendly label.
## Alternatives considered
Single unified status — rejected: violates principle, couples consent to payment.
## Implementation guardrails
- MUST NOT gate payout on `planStatus`; MUST NOT overwrite beneficiary responses; any transition change needs ADR update.
## Verification
- State-transition unit tests; batch≠item display tested; unknown status preserved.
